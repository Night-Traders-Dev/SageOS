
# RISC-V 64-bit Register-Based VM Design for SageVM
## A Comprehensive Architectural Analysis

---

## 1. Why RISC-V 64-bit for SageVM?

### 1.1 The Register vs Stack VM Evidence

Research from multiple academic sources strongly supports a register-based design:

**Key Findings:**
- Register VMs require ~46% fewer executed VM instructions than stack VMs (cite: web_search:16#1)
- Register VMs achieve 1.15x-1.48x speedup over stack VMs depending on dispatch mechanism (cite: web_search:16#2)
- Register code is ~25-26% larger than stack code, but extra fetch cost is negligible (1.07 extra loads per eliminated instruction) (cite: web_search:16#6)
- Register VMs excel at recursion and memory operations; stack VMs occasionally win on heavy arithmetic due to fewer operand fetches per dispatch (cite: web_search:16#4)
- With JIT compilation, register VMs maintain ~1.18x advantage over stack VMs (cite: web_search:16#4)

**Why RISC-V Specifically:**
1. **Clean, Minimal ISA**: RV64I has only ~50 base instructions - perfect for a VM ISA
2. **64-bit Native**: Matches modern architectures; eliminates 32-bit limitations
3. **Load-Store Architecture**: Separates computation from memory access - cleaner VM design
4. **Open Standard**: No licensing constraints; well-documented encoding schemes
5. **Proven Scalability**: RISC-V's modular design (M, A, F, D, C extensions) maps well to VM feature modules

## 2. RISC-V 64-bit VM Architecture Design

### 2.1 Register File Design

```
┌─────────────────────────────────────────────────────────┐
│                    REGISTER FILE (x0-x31)                │
├─────────────────────────────────────────────────────────┤
│  x0  │  zero  │ Hardwired zero (like RISC-V x0)        │
│  x1  │  ra    │ Return address                         │
│  x2  │  sp    │ Stack pointer (VM operand stack)       │
│  x3  │  gp    │ Global pointer (constant pool base)    │
│  x4  │  tp    │ Thread pointer (VM state)             │
│  x5  │  t0    │ Temporary / alternate link             │
│  x6  │  t1    │ Temporary                             │
│  x7  │  t2    │ Temporary                             │
│  x8  │  s0/fp │ Saved register / frame pointer        │
│  x9  │  s1    │ Saved register                        │
│ x10  │  a0    │ Argument / return value 0              │
│ x11  │  a1    │ Argument / return value 1              │
│ x12  │  a2    │ Argument 2                            │
│ x13  │  a3    │ Argument 3                            │
│ x14  │  a4    │ Argument 4                            │
│ x15  │  a5    │ Argument 5                            │
│ x16  │  a6    │ Argument 6                            │
│ x17  │  a7    │ Argument 7                            │
│ x18  │  s2    │ Saved register                        │
│ x19  │  s3    │ Saved register                        │
│ x20  │  s4    │ Saved register                        │
│ x21  │  s5    │ Saved register                        │
│ x22  │  s6    │ Saved register                        │
│ x23  │  s7    │ Saved register                        │
│ x24  │  s8    │ Saved register                        │
│ x25  │  s9    │ Saved register                        │
│ x26  │  s10   │ Saved register                        │
│ x27  │  s11   │ Saved register                        │
│ x28  │  t3    │ Temporary                             │
│ x29  │  t4    │ Temporary                             │
│ x30  │  t5    │ Temporary                             │
│ x31  │  t6    │ Temporary                             │
└─────────────────────────────────────────────────────────┘
```

**Key Design Decisions:**
- **32 general-purpose registers** (matching RISC-V standard)
- **64-bit width** for all registers (RV64I)
- **x0 is hardwired zero** - eliminates need for explicit zero constants
- **Dedicated sp register** - replaces implicit operand stack with explicit stack operations
- **Dedicated gp register** - points to constant pool for fast global access

### 2.2 VM State Structure

```c
typedef struct {
    // Register file
    uint64_t x[32];           // 32 x 64-bit registers
    
    // Program counter
    uint64_t pc;              // Bytecode instruction pointer
    
    // Memory regions

    uint64_t* constant_pool;  // Constant pool (typed values)
    uint8_t* heap;            // Object heap
    uint8_t* stack;           // Call stack (separate from operand stack)
    
    // Stack management
    uint64_t stack_top;       // Current stack position
    uint64_t frame_pointer;   // Current frame base
    
    // Exception handling
    uint64_t exception_handler; // PC of current catch block
    
    // GPU state (extension)
    void* gpu_context;        // GPU command buffer state
} SageVMState;
```

## 3. Instruction Encoding

### 3.1 RISC-V 64-bit Base Instruction Formats (RV64I)

RISC-V uses 6 instruction formats, all 32-bit fixed-width:

```
R-type (Register-Register):
┌──────┬─────┬─────┬─────┬─────┬──────┐
│ funct7 │ rs2 │ rs1 │ funct3 │ rd │ opcode │
│  7b   │ 5b  │ 5b  │  3b   │ 5b  │  7b   │
└──────┴─────┴─────┴─────┴─────┴──────┘

I-type (Immediate):
┌──────────┬─────┬─────┬─────┬──────┐
│ imm[11:0] │ rs1 │ funct3 │ rd │ opcode │
│   12b     │ 5b  │  3b   │ 5b  │  7b   │
└──────────┴─────┴─────┴─────┴──────┘

S-type (Store):
┌─────────┬─────┬─────┬─────┬─────┬──────┐
│imm[11:5]│ rs2 │ rs1 │ funct3│imm[4:0]│ opcode│
│   7b    │ 5b  │ 5b  │  3b  │  5b   │  7b   │
└─────────┴─────┴─────┴─────┴─────┴──────┘

B-type (Branch):
┌────┬─────┬─────┬─────┬────┬─────┬──────┐
│imm│ rs2 │ rs1 │ funct3│imm│ imm │ opcode│
│12│10:5│     │      │4:1│11  │       │
└────┴─────┴─────┴─────┴────┴─────┴──────┘

U-type (Upper Immediate):
┌──────────────┬─────┬──────┐
│  imm[31:12]  │ rd  │ opcode│
│     20b      │ 5b  │  7b   │
└──────────────┴─────┴──────┘

J-type (Jump):
┌────┬────────┬────┬─────┬──────┐
│imm │ imm    │imm │ rd  │ opcode│

│    │        │    │ 5b  │  7b   │

## 5. Constant Pool & Global Access

### 5.1 Constant Pool Design

Instead of the current stack-VM's per-chunk local constant mapping, a register VM uses a **global constant pool** with register-relative addressing:

```
Constant Pool Layout:
┌────────────────────────────────────────┐
│  Type Tag (1 byte) │ Value             │
├────────────────────────────────────────┤
│  TYPE_NIL (0)      │ (no value)        │
│  TYPE_BOOL (1)     │ 1 byte            │
│  TYPE_NUMBER (2)   │ 8 bytes (double)  │
│  TYPE_STRING (3)   │ 2-byte len + data │
│  TYPE_FUNCTION (4) │ 4-byte chunk idx  │
│  TYPE_CLASS (5)    │ 4-byte class idx  │
│  TYPE_ARRAY (6)    │ 4-byte array idx  │
│  TYPE_DICT (7)     │ 4-byte dict idx   │
│  TYPE_TUPLE (8)    │ 4-byte tuple idx  │
└────────────────────────────────────────┘
```

**Access Pattern:**
```
; Load constant at index 42 into register a0
LUI gp, %hi(constant_pool_base)     ; Set global pointer
ADDI gp, gp, %lo(constant_pool_base)
LD a0, 336(gp)                     ; 42 * 8 = 336 byte offset
```

Or using a custom instruction:
```
; Custom VM instruction for constant loading
LDC rd, idx                        ; Load constant at idx into rd
; Encoded as: LUI + ADDI + LD sequence (macro)
```

### 5.2 Global Variable Access

```
; Get global variable "foo"
LUI a0, %hi(global_symbol_table)
LD a1, %lo(foo_offset)(a0)         ; a1 = address of "foo"
LD a2, 0(a1)                        ; a2 = value of "foo"

; Set global variable "foo"
SD a2, 0(a1)                        ; foo = a2
```

## 6. Translation from Stack to Register VM

### 6.1 Stack-to-Register Translation Algorithm

The key challenge is translating stack-based bytecode to register-based bytecode. This is analogous to register allocation in a compiler:

python```
def translate_stack_to_register(stack_bytecode):
    "Translate stack VM bytecode to register VM bytecode.

    Uses a simple stack-to-register mapping during translation.
"
    reg_stack = []          # Virtual stack of register assignments
    next_reg = 10           # Start allocating from a0 (x10)
    MAX_REG = 17          # Up to a7 (x17) for operands
    
    for instr in stack_bytecode:
        if instr.opcode == OP_CONSTANT:
            # Load constant into new register
            rd = alloc_reg()
            emit(f"LDC {rd}, {instr.operand}")
            reg_stack.append(rd)
            
        elif instr.opcode == OP_ADD:
            # Pop two operands, add, push result
            rs2 = reg_stack.pop()
            rs1 = reg_stack.pop()
            rd = alloc_reg()
            emit(f"ADD {rd}, {rs1}, {rs2}")
            reg_stack.append(rd)
            free_reg(rs1)
            free_reg(rs2)
            
        elif instr.opcode == OP_GET_GLOBAL:
            rd = alloc_reg()
            emit(f"LDG {rd}, {instr.operand}")  # Load global
            reg_stack.append(rd)
            
        elif instr.opcode == OP_CALL:
            # Prepare arguments in a0-a7
            argc = instr.operand
            args = []
            for i in range(argc):
                args.append(reg_stack.pop())
            args.reverse()
            
            for i, arg in enumerate(args):
                emit(f"MV a{i}, {arg}")
                free_reg(arg)
            
            emit(f"CALL {instr.function_idx}")
            rd = alloc_reg()
            emit(f"MV {rd}, a0")  # Capture return value
            reg_stack.append(rd)
            
        elif instr.opcode == OP_JUMP_IF_FALSE:
            cond = reg_stack.pop()
            emit(f"BEQZ {cond}, {instr.target}")
            free_reg(cond)
            
        # ... etc for all opcodes
    
    return register_bytecode
```

### 6.2 Register Allocation Strategy

For a VM, we can use a **simple greedy allocation** rather than graph coloring:

```
Strategy: Linear Scan with Spilling

1. Maintain a virtual register stack mapping stack positions to physical registers
2. When stack depth exceeds available registers (a0-a7 = 8 regs), spill to memory
3. Use register x8 (s0) as frame pointer for spilled values
4. Reuse freed registers immediately

Physical Register Budget:
- a0-a7: 8 registers for operands and arguments
- t0-t6: 7 registers for temporaries
- s0-s11: 12 registers for local variables (if function-local allocation)
```

### 6.3 Example Translation

**Stack VM code (original):**
```
OP_CONSTANT 0       ; push 42
OP_CONSTANT 1       ; push 10
OP_ADD              ; pop 2, push result
OP_SET_GLOBAL 2     ; pop 1, store to "x"
```

**Register VM code (translated):**
```asm
LDC a0, 0           ; a0 = 42 (constant 0)
LDC a1, 1           ; a1 = 10 (constant 1)
ADD a0, a0, a1      ; a0 = a0 + a1 = 52
SDG a0, 2           ; global[2] = a0 (store "x")
```

**Instruction count comparison:**
- Stack VM: 4 instructions, 4 dispatches, 4 stack operations
- Register VM: 3 instructions, 3 dispatches, 0 stack operations

## 7. Binary Format (.sgrv - Sage RISC-V)

### 7.1 File Format

```
┌─────────────────────────────────────────────────────────────┐
│  Magic: "SGRV" (4 bytes)                                    │
│  Version: major (1 byte), minor (1 byte)                   │
│  Flags: 64-bit mode, extensions present (2 bytes)            │
├─────────────────────────────────────────────────────────────┤
│  Section Table Offset (4 bytes)                             │
│  Number of Sections (2 bytes)                                │
├─────────────────────────────────────────────────────────────┤
│  SECTIONS:                                                  │
│    .text    - Executable bytecode (RISC-V 32-bit instrs)   │
│    .rodata  - Constant pool                                  │
│    .symtab  - Symbol table (function/class names)             │
│    .rel     - Relocation table (for dynamic linking)         │
│    .meta    - VM metadata (entry point, main chunk, etc.)     │
│    .gpu     - GPU command descriptors (optional)             │
└─────────────────────────────────────────────────────────────┘
```

### 7.2 Instruction Encoding

All instructions are **32-bit fixed-width**, aligned on 4-byte boundaries:

```
Text Section:
┌─────────────────────────────────────────────────────────────┐
│  Instruction 0 (4 bytes)                                   │
│  Instruction 1 (4 bytes)                                   │
│  ...                                                        │
│  Instruction N (4 bytes)                                   │
└─────────────────────────────────────────────────────────────┘

Benefits:
- Easy PC calculation: PC = base + (idx * 4)
- No variable-length decoding
- Branch targets are instruction indices (not byte offsets)
- Better instruction cache utilization
```

### 7.3 Diagnostic Tools
The Sage RISC-V format is fully supported by the unified `sagevm` CLI tools.
- **Disassembler**: Use `sagevm dis <file.sgrv>` to produce standard RISC-V assembly output.
- **Hexdump**: Use `sagevm hex <file.sgrv>` to inspect the low-level section headers and raw instruction bytes.

### 7.4 Comparison with Current .sgvm Format

| Feature | Current .sgvm (Stack) | Proposed .sgrv (RISC-V) |
|---------|---------------------|-------------------------|
| Instruction width | Variable (1-5 bytes) | Fixed 32-bit (4 bytes) |
| Opcode encoding | 1 byte + operands | 7-bit opcode + funct3/7 |
| Operand encoding | Inline, variable | Register fields (5-bit each) |
| Constant access | Per-chunk local→global map | Global pool + gp-relative |
| Stack operations | Implicit (push/pop) | Explicit (sp-relative) |
| Function calls | OP_CALL with arg count | CALL with a0-a7 convention |
| Code density | High (compact) | Lower (~25% larger) |
| Dispatch overhead | High (decode per instr) | Lower (uniform decode) |
| Branch prediction | Harder (variable length) | Easier (fixed length) |

## 8. Implementation Strategy for SageVM

### 8.1 Phase 1: Core RV64I Interpreter

Implement the base integer instruction set in pure SageLang:

```sage
# Core interpreter loop (conceptual)
proc execute_riscv_vm(bytecode, constant_pool):
    var pc = 0
    var x = array(32, 0)   # 32 registers, 64-bit values
    x[0] = 0               # x0 = zero (hardwired)
    
    while true:
        let instr = decode_instruction(bytecode, pc)
        let opcode = instr.opcode
        
        if opcode == OP_ADD:
            x[instr.rd] = x[instr.rs1] + x[instr.rs2]
            pc = pc + 4
        elif opcode == OP_ADDI:
            x[instr.rd] = x[instr.rs1] + sign_extend(instr.imm, 12)
            pc = pc + 4
        elif opcode == OP_LD:
            let addr = x[instr.rs1] + sign_extend(instr.imm, 12)
            x[instr.rd] = load_64bit(addr)
            pc = pc + 4
        elif opcode == OP_SD:
            let addr = x[instr.rs1] + sign_extend(instr.imm, 12)
            store_64bit(addr, x[instr.rs2])
            pc = pc + 4
        elif opcode == OP_BEQ:
            if x[instr.rs1] == x[instr.rs2]:
                pc = pc + sign_extend(instr.imm, 13)
            else:
                pc = pc + 4
        elif opcode == OP_JAL:
            x[instr.rd] = pc + 4
            pc = pc + sign_extend(instr.imm, 21)
        elif opcode == OP_JALR:
            let target = x[instr.rs1] + sign_extend(instr.imm, 12)
            x[instr.rd] = pc + 4
            pc = target & ~1
        elif opcode == OP_VMSYS:
            handle_vm_system_call(instr)
            pc = pc + 4
        elif opcode == OP_HALT:
            break
```

### 8.2 Phase 2: Stack-to-Register Compiler

Build a translator from `.svm` (stack) to `.sgrv` (register):

```sage
class StackToRiscVTranslator:
    proc translate(self, svm_file, sgrv_file):
        let stack_bytecode = parse_svm(svm_file)
        let reg_bytecode = []
        let reg_allocator = LinearScanAllocator()
        
        for instr in stack_bytecode:
            let translated = self.translate_instruction(instr, reg_allocator)
            push(reg_bytecode, translated)
        
        write_sgrv(sgrv_file, reg_bytecode)
    
    proc translate_instruction(self, instr, allocator):
        if instr.opcode == OP_CONSTANT:
            let rd = allocator.alloc()
            return [make_ldc(rd, instr.operand)]
        elif instr.opcode == OP_ADD:
            let rs2 = allocator.pop()
            let rs1 = allocator.pop()
            let rd = allocator.alloc()
            allocator.free(rs1)
            allocator.free(rs2)
            return [make_add(rd, rs1, rs2)]
        # ... etc
```

### 8.4 Phase 4: JIT Compilation Target

A register VM is an ideal IR for JIT compilation to native code:

```
SageLang Source
      ↓
Sage Compiler (C) → .svm (stack IR)
      ↓
sgvmc_riscv (translator) → .sgrv (register IR)
      ↓
┌─────────────────────────────────────────┐
│  Path A: Interpret (pure Sage)          │
│  Path B: JIT to native (RISC-V host)    │
│  Path C: JIT to native (x86_64 host)    │
│  Path D: JIT to native (ARM64 host)     │
└─────────────────────────────────────────┘
```

The RISC-V IR maps almost 1:1 to native RISC-V instructions, making JIT compilation trivial for RISC-V hosts. For x86_64/ARM64, each RISC-V instruction expands to a small sequence of native instructions.

## 10. Risks & Challenges

### 10.1 Implementation Complexity

- **Register allocation**: More complex than stack manipulation
- **Calling convention**: Must be strictly enforced across all generated code
- **Spilling**: When expression complexity exceeds register budget

### 10.2 Code Size Increase

- 25% larger bytecode means more memory usage
- More instruction cache pressure
- Mitigation: Use RISC-V compressed extension (RVC) for 16-bit instructions

### 10.3 Translation Complexity

- Stack→register translation requires liveness analysis
- Exception handling stack unwinding becomes more complex
- Debugging information mapping is harder

### 10.4 Pure SageLang Implementation

- RISC-V's fixed 32-bit encoding is actually **simpler** to decode than variable-length stack VM
- Bit manipulation in SageLang is straightforward
- The uniform instruction format reduces branch complexity in the interpreter

---

## 11. Conclusion

A RISC-V 64-bit register-based VM design for SageVM offers:

1. **Proven performance gains**: 15-48% faster interpretation, 46% fewer instructions
2. **Cleaner architecture**: Load-store design separates computation from memory
3. **JIT-ready**: Register IR is the natural input for native code generation
4. **Open standard**: RISC-V is well-documented, extensible, and license-free
5. **Educational value**: Teaches real CPU architecture concepts through VM implementation
6. **Future-proof**: 64-bit design handles modern data sizes natively

The tradeoff is ~25% larger bytecode and more complex translation from stack IR, but the performance and architectural benefits strongly justify the redesign for a VM that aims to be both a reference implementation and a production-capable execution engine.
